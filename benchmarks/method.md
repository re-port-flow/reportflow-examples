# PDF 生成ベンチマーク 測定仕様

Re:port Flow の PDF 生成 API について、**何を・どの条件で・どう測り・何を失敗と数えるか**を定義する。
`benchmarks/run.mjs` はこの手順の実装であり、実装とこの文書が食い違った場合は**この文書を正**とする。

公開されている測定結果は <https://lp.re-port-flow.com/benchmarks/> にある。

---

## 1. 何を測るか（測定対象の定義）

このベンチマークが測るのは、**API 利用者のクライアントから観測できる所要時間**である。

```
クライアント → (インターネット) → CDN / ロードバランサ → API → (生成・保存)
```

したがって測定値には次が含まれる。

- クライアントの所在地から API エンドポイントまでのネットワーク往復
- TLS ハンドシェイク（接続が再利用されない場合）
- CDN / ロードバランサの転送
- テンプレート・フォント・画像の読み込み、レイアウト計算、PDF 描画
- 生成物の保存（非同期の完了判定に含まれる）
- レスポンス本文（PDF / ZIP）の転送

**サーバ内部のレンダリング時間だけを取り出した値ではない。** 内部の内訳は公開 API からは観測できない。
数値を比較する際は、クライアントの所在地と回線が結果に直接効くことに注意すること。

### 指標

| 指標 | 対象 | 定義 |
|---|---|---|
| `latencyMs`（同期） | `sync/single`, `sync/multiple` | リクエスト送信開始 → レスポンス本文（PDF / ZIP）の受信完了 |
| `acceptedMs`（非同期） | `async/single`, `async/multiple` | リクエスト送信開始 → `202 Accepted` の受信完了。**呼び出し側がブロックされる時間** |
| `latencyMs`（非同期） | `async/single`, `async/multiple` | リクエスト送信開始 → **全ファイル**がダウンロード可能になるまで（完了時間） |

非同期の完了時間は「そのリクエストで指定した全ファイルが `GET /file/download/{requestId}/{fileId}` で
200 を返すようになった時刻」で確定する。生成中は 409 `FILE_NOT_READY`（`Retry-After` 付き）が返る。404 は不在、422 は生成失敗として停止する。

**完了検知の基準**：`contents` はおおむね配列順に処理され、各ファイルは生成が終わった時点で個別に
取得可能になる（外形的な観察。実装が変わればこの前提も変わりうる）。そこでまず**配列末尾のファイル**を
監視し、200 になってから残りを 1 巡して全件そろっていることを確認する。この 1 巡があるので、
順序の前提が崩れても取りこぼさない。

計測値として採るのは**末尾のファイルが 200 になった時刻**である。確認の 1 巡はダウンロードのレート上限に
合わせて 750 ms 間隔で回るため（50 件なら 1 巡だけで 37 秒）、その時間を完了時間に足すと**測定側の
ペーシングを製品の遅さとして計上してしまう**。ただし 1 巡の途中で 409 FILE_NOT_READY を観測したファイル（＝本当にまだ
生成中だった）があれば、そのファイルが 200 になった時刻へ更新する。全ファイルを毎周叩く方式を採らないのも
同じ理由で、こちらがレート上限にぶつかった待ち時間が完了時間に混ざるため。

## 2. 条件（測定マトリクス）

### 2.1 エンドポイント（同期・非同期 × 単一・複数）

| エンドポイント | 返るもの | サーバ側タイムアウト | レート上限 |
|---|---|---|---|
| `POST /file/sync/single` | PDF バイナリ | 120 秒 | 30 req/分 |
| `POST /file/sync/multiple` | ZIP バイナリ | 120 秒 | 30 req/分 |
| `POST /file/async/single` | `202` + `requestId` | なし | 100 req/分 |
| `POST /file/async/multiple` | `202` + `requestId` | なし | 100 req/分 |

上限値の一次情報は [制限事項](https://doc.re-port-flow.com/docs/limitations)。

### 2.2 明細行数とページ数

**入力として動かすのは明細行数（`lineItems`）で、ページ数はその結果として観測する値**である。
1 ページに収まる行数はテンプレートのレイアウトで決まるため、行数からページ数を先に決め打ちできない。

既定のマトリクスは 5 行 / 50 行 / 200 行。行以外のフィールド（請求先名・件名・備考など）は全条件で固定し、
変動要因を明細行数だけに絞る。

ページ数は生成された PDF から推定する（`/Type /Page` の出現数とページツリーの `/Count` を突き合わせる）。
オブジェクトストリームで圧縮された PDF ではこの方法が使えないため、その場合は**推測せず「未判定」**として
結果 JSON に `pageCount: null` を残す。結果の `pageCountMethod` に判定方法が入る。

### 2.3 件数（バッチサイズ）

`sync/multiple` / `async/multiple` の `contents` 配列の要素数。**既定は 5 件のみ**（上限も 5 件。理由は §5-10）。
単一生成（1 件）と並べて読むことで、件数を増やしたときに 1 件あたりの時間がどう変わるかが分かる。

1 リクエスト内のファイルはまとめて並行処理されるため、**所要時間は件数に対して線形にならない**
（1 件あたりに換算した時間は件数が増えるほど小さくなる）。並行数は内部の実装値で外からは分からず、
変わりうるので、この値に依存した判定はしない（§1 の完了検知も、処理順の前提が崩れた場合を
確認の 1 巡で拾う作りにしてある）。

### 2.4 試行回数とウォームアップ

| 項目 | 既定値 | 理由 |
|---|---|---|
| ウォームアップ | 2 回（複数生成は 1 回） | コールドスタート（サーバー側の起動直後・キャッシュ未構築・TLS 接続確立）を統計から外す。**破棄する**（統計にも失敗件数にも含めない） |
| 試行回数 | 20 回（複数生成は 10 回） | P95 が最大値と区別できる最小が 20 回（§4）。複数生成は 1 試行あたりの生成ファイル数が増えるため回数を落とす（その結果 P95 は最大値と一致する） |
| 同時実行数 | 1（逐次） | **レイテンシの測定であって、スループット測定・負荷試験ではない** |

ウォームアップも本試行も**同一の入力**で行う。

### 2.5 リクエストのペーシング

自分でレート上限にぶつかると、その待ち時間が測定値に混ざる。各エンドポイント種別のレート上限の
**80%**（`rateLimitUtilization`）を上限としてリクエスト間隔を空ける。この待機は**計測窓の外**で消化する。

- 同期: 30 req/分 × 0.8 → 2,500 ms 間隔
- 非同期: 100 req/分 × 0.8 → 750 ms 間隔
- ダウンロード（完了ポーリング）: 100 req/分 × 0.8 → 750 ms 間隔

### 2.6 環境として記録する項目

結果 JSON に次を残す。**クライアントの所在地と回線は自動判定できないため、環境変数で申告する。**
未設定なら「未申告」と記録され、公開時もそのまま「未申告」と出す（推測で埋めない）。

| 項目 | 取得元 |
|---|---|
| API ベース URL / API バージョン | 設定ファイル |
| 実行日時（開始・終了、UTC） | 実行時 |
| クライアントの所在地 | 環境変数 `BENCHMARK_CLIENT_LOCATION` |
| クライアントの回線 | 環境変数 `BENCHMARK_CLIENT_NETWORK` |
| Node.js バージョン / OS / CPU アーキテクチャ | `process` |
| テンプレート（名称・ギャラリー URL） | 設定ファイル |
| デザイン ID | **公開しない。** 同一実行内の照合用に SHA-256 の先頭 12 桁だけ残す |

サーバー側の構成（台数・インスタンスサイズ・リージョン）は非公開のため、結果には含めない。
データ保管地が AWS 東京リージョンであることは[サービス事実表](https://lp.re-port-flow.com/service-facts/)に記載がある。

## 3. 失敗判定

次のいずれかに当たった試行を**失敗**として数え、成功した試行だけで統計を取る。失敗件数と内訳は
結果 JSON と公開ページの両方に必ず出す（失敗を隠して中央値だけ出さない）。

| 分類 | 条件 |
|---|---|
| `http_error` | 2xx 以外が返った（生成待ちの409 FILE_NOT_READY・429を除く） |
| `timeout` | クライアント側のタイムアウトに達した（同期 130 秒 / ダウンロード 60 秒） |
| `network_error` | 接続断・DNS 失敗など、レスポンスを受け取れなかった |
| `invalid_body` | 2xx だが中身が期待と違う（PDF が `%PDF-` で始まらない、ZIP のマジックナンバーが違う、`202` の `files` 件数が要求と一致しない） |
| `poll_timeout` | 非同期で、完了期限（既定 15 分）内に全ファイルがダウンロード可能にならなかった |
| `rate_limit_exhausted` | 429 が続き、設定された再送の上限（既定3回）に達した |

### リトライの扱い

- **生成の失敗は自動リトライしない。** 成功するまで叩き直すと、実際の失敗率が結果から消える。
- **429 は設定が許す場合だけ待って投げ直す。** `maxRateLimitRetries: 0` では生成POSTもダウンロードGETも再送せず停止する。 429 はリクエストが受理されておらず PDF も生成されていないため、
  再送しても二重生成にならない。生成POSTは `Retry-After` ヘッダの秒数に従い、設定された上限（既定3回）まで。ダウンロードGETは有効な場合、完了期限まで待機する。
- **待ち直した試行は成功しても標本に含めない。** 計測は最初の送信から始まっているので、
  `Retry-After` の待機（既定 60 秒）がそのままレイテンシとして乗る。成功はしていても製品の所要時間では
  ないため統計から外し、`rateLimited` の件数としてだけ残す。結果 JSON では
  `latencyMs.samples` が `iterations` より少なくなるので、除外が起きたことは数字から追える。

## 4. 統計

| 値 | 定義 |
|---|---|
| 中央値 | 標本数が奇数なら中央の値、偶数なら中央 2 値の平均 |
| P95 | **最近傍順位法**。昇順に並べて `ceil(0.95 × n)` 番目の値。補間はしない |
| 最小 / 最大 / 平均 | そのまま |
| 標本数 | 成功した試行の数（ウォームアップと 429 は含まない） |

**P95 は試行回数 20 回以上でないと意味を持たない。** 最近傍順位法では `n < 20` のとき `ceil(0.95n) = n` と
なり、P95 が常に最大値と一致するため。試行回数を 20 未満にした場合、実行時に警告が出る。

n = 20 の P95 は「20 標本のうち上から 2 番目」であり、真の 95 パーセンタイルの推定としては粗い。
**この粗さを承知の上で読む値**であることを公開ページにも明記する。

## 5. この測定で分からないこと（例外・制限事項）

正しく読むために、測れていないことを先に挙げる。

1. **スループットではない。** 同時実行数 1 の逐次測定なので、「1 分あたり何件さばけるか」は分からない。
   並列実行時の挙動はレート上限（同期 30 / 非同期 100 req/分）とサーバー側の容量に支配される。
2. **1 テンプレートの結果である。** 画像点数・フォント種類・図形数・グラフの有無で生成時間は変わる。
   別のテンプレートに数値をそのまま当てはめられない。
3. **クライアントの所在地・回線に依存する。** 測定値にはインターネット区間が含まれる。
   別の場所から測れば別の値になる。
4. **他ワークスペースの負荷を制御できない。** 本番環境は共有基盤であり、測定時点の全体負荷は観測できない。
5. **非同期の完了時間にはポーリング間隔の分解能がある。** 完了時刻はポーリングで検出するため、
   観測値にはポーリング間隔（既定1,000 ms、409のRetry-Afterが長ければそちらを優先）と通信・ペーシングの時間が含まれる。
6. **ページ数は推定値である。** §2.2 のとおり、判定できない場合は「未判定」として残す。
7. **`sync/multiple` のページ数は測っていない。** レスポンスが ZIP で、展開しないと中身を読めないため。
8. **SLA ではない。** 測定日時点の実測値であり、将来の性能を保証するものではない。
   稼働率・性能に関する契約上の扱いは[利用規約](https://lp.re-port-flow.com/terms/)による。
9. **測定時のサーバー側の状態は外からは分からない。**
   サーバー側がどのような内部状態で応答したかは、公開 API のレスポンスからは判別できない。
   同じ入力でも、サーバー側の状況によって所要時間も出力サイズも変わりうる。
   **1 回の測定結果は、その時刻のその状態を測ったものとして扱う**こと。日を変えて測り直し、
   値が大きく動く場合は、条件を変えていないか・サーバー側で何か起きていないかを疑う。

10. **件数の大きいバッチは共有基盤に負荷をかける。**
   本番環境は他の利用者と共有している。件数の大きいバッチを繰り返し投げると、
   自分の測定のために他の利用者の生成を遅らせることになる。

   このため既定のマトリクスでは**件数の上限を 5 件**にしてある（`maxBatchSize`）。
   上限を超える設定は実行前にエラーになる。大きい件数をどうしても測る必要がある場合は、
   影響範囲を確認したうえで上限を上げること。連続して失敗した場合は
   `consecutiveFailureLimit`（既定 3）でその場で中断する。

## 6. 再現手順

### 試行記録と停止

`--evidence-out` を指定すると、公開集計とは別に非公開 JSONL を保存する。
ウォームアップ・失敗も残し、試行の開始終了時刻、未丸めの計測値、request/file 識別子で
外部の証跡と照合できるようにする。応答識別子が欠ける場合は null / 空配列であり、推測で補わない。
生成経路はこのハーネスだけでは判定できないため `unverified` とし、HTTP 成功を経路の証明に使わない。
公開集計 JSON の構造バージョンは 1 のまま維持し、非公開記録をそのまま配布しない。

`--max-duration-ms`、SIGINT、SIGTERM ではクライアントの待機・通信と後続送信を止める。
サーバーが受理済みの処理は停止できない。部分結果は `abortedEarly: true`、終了コード 2 とする。
JSONL の trial_start に対応する trial_end がない場合も、その試行の成功を推定しない。
公開結果と非公開記録は排他作成し、保存済み結果を上書きしない。

実行方法は [benchmarks/README.md](./README.md) を参照。

測定結果を公開値として扱うには、次を満たすこと。

- `config.default.json` を無改変で使う（改変したなら、その差分を結果と一緒に示す）
- 試行回数 20 以上（複数生成は 10 以上）
- 失敗件数・429 発生回数を結果と併記する
- クライアントの所在地・回線を申告する（`BENCHMARK_CLIENT_LOCATION` / `BENCHMARK_CLIENT_NETWORK`）
